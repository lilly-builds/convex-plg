# Working on Convex Product-Led Growth Signal Review

This repository is a small Convex-backed prototype for an explainable product-led growth workflow. It turns **labeled synthetic team signals** into one reviewable team case, a recommended human response, and a test-only delivery preview.

It is intentionally not a production outreach system. Good changes preserve that distinction.

## Start here

- Read [`README.md`](README.md) for the product story, safety boundary, local setup, and project map.
- Read [`src/policy.ts`](src/policy.ts) before changing a recommendation or eligibility rule.
- Read [`src/fixtures.ts`](src/fixtures.ts) and [`test/`](test) before changing policy behavior; fixtures are the contract for normal and edge cases.
- Read [`convex/reviews.ts`](convex/reviews.ts) before changing persisted behavior, the queue, or the demo reset.
- Read [`docs/demo-storyboard.md`](docs/demo-storyboard.md) when changing reviewer-facing copy or the demo flow.

## Runtime flow

`main.tsx` reads `VITE_CONVEX_URL`. When it is present, it creates a `ConvexReactClient` and renders the real queue. When it is absent, the app renders an explicit offline message rather than a fake local queue.

The normal path is:

1. A sandbox button calls `reviews.resetDemo` and then `reviews.seedSyntheticFixture`.
2. `reviews.seedSyntheticFixture` calls the policy, saves an evaluation, evidence rows, a candidate when eligible, recipient targets, and an event history.
3. `reviews.listCandidates` and `reviews.getCandidateDetails` update the React UI through Convex queries.
4. The reviewer can record `not_now` or `suppress`; the backend closes the case, stops pending targets, and records a team policy state.
5. A test-only delivery mutation schedules `testDelivery.deliver`, which records `failed` or `succeeded` without calling Slack, email, or another network service.

## State and lifecycle

- **Hold:** the team did not meet a required evidence gate; no candidate or delivery target is created.
- **Suppress:** an explicit stop condition such as no-contact, partner attribution, existing owner/open case, or cooldown blocked the review.
- **Open candidate:** a single review exists and is visible in the queue.
- **Route upgrade:** a stronger later signal updates the same open candidate and supersedes obsolete unsent targets.
- **Terminal decision:** `not_now` or `suppress` closes the candidate and stops pending or failed delivery targets.
- **Delivery state:** only `pending`, simulated `failed`, and simulated `succeeded` behavior is exercised. No provider integration exists.

## Product model

The app answers one question: **What should we do next for this team, and why?**

A team can be held, suppressed, or surfaced as one shared review:

- **Emerging:** real product momentum worth watching, but no urgent request or confirmed pressure.
- **Pressure:** sustained usage pressure against a confirmed team-level hard limit.
- **Direct:** an open, authorized enterprise-style request such as security, SSO, legal, procurement, contract, or compliance.
- **Both:** pressure and a direct request. Treat the request as urgent while keeping both pieces of evidence.

The app must never turn incomplete, unauthorized, unattributed, suppressed, already-owned, or cooldown-bound input into a review.

## Non-negotiable safety boundary

- Use **synthetic labeled records only**.
- Never add real customer, application, end-user, secret, schema, document, or environment-variable data.
- Never add live Slack, email, outreach, or a claim that a message was sent.
- Keep the customer reply a **draft** and the delivery surface a **test-only preview**.
- Preserve the allowlisted demo reset: it may affect only `demo:default` data and must not remove unrelated test or local records.
- Do not weaken fixtures, limits, retries, source checks, or suppressions just to make a test pass.

A production version would require explicit source ownership, permitted-use review, retention rules, least-privilege access, owner/no-contact checks, and an approved channel for every delivery.

## Architecture at a glance

```text
Synthetic fixture
  → policy evaluation
  → Convex mutation persists evidence, case, recipients, and history
  → real-time queue and detail view
  → human decision / customer-reply draft
  → simulated delivery result and recovery history
```

Key backend records live in the Convex schema:

- `teams` and `evidenceRecords` explain the case;
- `candidates` is the single shared team review;
- `deliveryTargets` and `deliveryAttempts` make test delivery observable and idempotent;
- `candidateEvents` preserves the audit trail;
- `teamPolicyStates` holds cooldown and suppression-related state.

## Invariants to preserve

1. One qualifying team becomes one candidate, even during parallel evaluation.
2. A route upgrade changes the existing candidate; it does not make a duplicate.
3. Each configured recipient has one chosen channel: Slack **or** email, never both.
4. Existing recipient snapshots remain stable unless an authorized route upgrade changes them.
5. A failed test delivery can recover once without a duplicate success.
6. Pause, suppress, existing owner, partner attribution, and no-contact states stop pending work.
7. The app should make the evidence and next human action understandable without reading logs.

## Local development and verification

```sh
npm install
npx convex dev        # keep running in one terminal
npm run dev           # web app in another terminal
```

Before submitting a behavior change, run the narrowest relevant test and then:

```sh
npm test
npm run check
npm run build
npm run verify:demo-reset
npm run verify:local
```

`verify:local` exercises the persisted Convex path, including all fixtures, upgrades, duplicate handling, simulated outage/recovery, and workload. It requires the local Convex backend to be running and the synthetic sandbox to be enabled. It is local evidence only, not production proof.

## Writing and UI guidance

- Prefer plain-language explanations over internal labels or generic growth jargon.
- “Prepare response” should reveal a customer-facing draft, not an internal task assignment.
- Keep the reason a team appeared separate from the message we might send them.
- Keep safety state visible: synthetic data, draft-only response, and test-only delivery should be clear in the interface.
- Treat screenshots, walkthrough copy, and README claims as product surfaces: they must match the actual behavior.
